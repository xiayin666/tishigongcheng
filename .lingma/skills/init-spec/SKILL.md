# Init-SPEC 技能 - 项目规格文档生成器

## 📋 技能概述

本技能帮助用户按照 **SPEC 开发范式** 系统化地规划软件项目，生成4个核心开发文档，确保项目从需求到测试的完整性和规范性。

## 🎯 适用场景

- ✅ 开始新的软件开发项目
- ✅ 需要规范化项目文档体系
- ✅ 团队协作前的需求对齐
- ✅ 课程设计或毕业设计的开题准备
- ✅ 创新创业大赛的项目计划书编写

## 📝 输出文档

按以下顺序生成4个规范文档：

### 1️⃣ requirement.md - 需求文档（用户视角）
**定位**：从用户角度描述功能需求和业务价值

**包含内容**：
- 用户目标和痛点
- 功能需求列表（含优先级）
- 用户故事（User Stories）
- 使用流程说明
- 输入输出示例
- 约束条件和验收标准

**参考模板**：`assets/requirement-example.md`

---

### 2️⃣ spec.md - 技术规格说明（技术视角）
**定位**：从技术角度定义系统架构和实现方案

**包含内容**：
- 项目概述和技术选型
- 文件结构设计
- 配置参数说明
- 核心功能模块划分
- 数据流转图
- 输出格式规范

**参考模板**：`assets/spec-example.md`

---

### 3️⃣ api.md - API设计文档（开发视角）
**定位**：详细的接口设计和伪代码实现

**包含内容**：
- 模块结构和函数列表
- 全局变量和常量定义
- 每个方法的详细设计：
  - 功能描述
  - 参数说明（类型、含义）
  - 返回值说明
  - 异常处理
  - **伪代码实现**（关键！）
- 数据流转图

**参考模板**：`assets/api-example.md`

---

### 4️⃣ test.md - 测试用例文档（质量保障）
**定位**：完整的测试计划和用例设计

**包含内容**：
- 测试目标和范围
- 单元测试用例（表格形式）
- 集成测试用例
- 端到端测试场景
- 测试步骤和工具
- 预期输出验证标准

**参考模板**：`assets/test-example.md`

## 🔄 执行流程

### 第一步：收集项目信息
向用户询问以下关键信息：

1. **项目基本信息**
   - 项目名称和简要描述
   - 解决的核心问题
   - 目标用户群体

2. **功能需求**
   - 主要功能列表
   - 优先级排序（必须有/应该有/可以有）
   - 特殊要求或限制

3. **技术偏好**
   - 编程语言和框架
   - 是否需要API接口
   - 数据存储方式

4. **其他信息**
   - 是否有参考案例
   - 预期的项目规模
   - 时间或资源限制

### 第二步：生成 requirement.md
基于用户需求，生成用户视角的需求文档，重点突出：
- 用户价值和痛点解决
- 清晰的功能列表
- 具体的使用场景

**等待用户确认后再继续**

### 第三步：生成 spec.md
根据需求文档，转化为技术规格说明：
- 选择合适的技术方案
- 设计合理的文件结构
- 明确配置和依赖关系

**等待用户确认后再继续**

### 第四步：生成 api.md
基于技术规格，设计详细的API和函数：
- 为每个函数编写伪代码
- 定义清晰的输入输出
- 考虑异常处理和边界情况

**等待用户确认后再继续**

### 第五步：生成 test.md
最后设计完整的测试方案：
- 覆盖所有核心功能
- 包含正常和异常场景
- 提供可执行的测试步骤

## 💡 使用示例

**用户**: "我想开发一个天气查询工具，能帮我规划设计吗？"

**AI助手**:
```
我将按照SPEC范式帮你规划这个项目。首先了解一些细节：

1. 这个工具需要支持哪些城市？（国内/全球）
2. 需要显示哪些天气信息？（温度、湿度、风力等）
3. 是否需要历史天气或预报功能？
4. 你希望用什么语言开发？（Python/Java等）
5. 是否需要图形界面还是命令行即可？

请告诉我你的想法，我会据此生成 requirement.md 文档。
```

**用户提供信息后**:
```
好的，根据你的需求，我生成了 requirement.md：

[展示 requirement.md 内容]

请阅读这份需求文档，如果没有问题，请回复"继续"，我将生成 spec.md 技术规格文档。
```

## ⚠️ 注意事项

### 必须遵守的原则
1. **逐步确认**：每生成一个文档后，必须等待用户确认才能继续
2. **基于真实需求**：所有内容必须基于用户提供的信息，不编造
3. **伪代码要详细**：api.md 中的伪代码应足够详细，便于后续直接编码
4. **测试要全面**：test.md 应覆盖正常流程和异常场景

### 常见问题避免
- ❌ 不要跳过任何文档
- ❌ 不要一次性生成所有文档
- ❌ 不要使用模糊的描述（如"等等"、"其他功能"）
- ❌ 不要在伪代码中省略关键逻辑
- ✅ 使用表格展示结构化数据
- ✅ 提供具体的示例和案例
- ✅ 保持文档之间的逻辑一致性

## 📊 质量标准

生成的文档应满足：

| 维度 | 标准 |
|------|------|
| **完整性** | 4个文档齐全，无遗漏 |
| **准确性** | 技术描述准确，无错误 |
| **可执行性** | 开发人员可直接根据文档编码 |
| **可读性** | 结构清晰，排版美观 |
| **一致性** | 各文档之间逻辑连贯 |
