# init-spec Skill

## 用途
帮助用户按照 SPEC 开发范式初始化项目，生成四个核心开发文档：
- spec.md - 项目规格说明
- requirement.md - 需求文档
- api.md - API 设计文档（包含函数伪代码）
- test.md - 测试计划文档

## 使用场景
当用户想要开始一个新项目开发，需要按照规范的 SPEC 范式进行规划时使用。

## 执行流程

### 第一步：生成 spec.md
1. 询问用户的开发需求
2. 基于用户需求生成 spec.md 文件，包含：
   - 项目概述
   - 功能目标
   - 技术选型建议
   - 架构设计思路

### 第二步：生成 requirement.md
1. 等待用户确认 spec.md 无误
2. 生成 requirement.md 文件，包含：
   - 详细功能需求列表
   - 用户故事
   - 验收标准
   - 优先级划分

### 第三步：生成 api.md
1. 等待用户确认 requirement.md 无误
2. 生成 api.md 文件，包含：
   - API 接口定义
   - 每个函数的伪代码
   - 输入输出规范
   - 数据结构设计

### 第四步：生成 test.md
1. 等待用户确认 api.md 无误
2. 生成 test.md 文件，包含：
   - 单元测试计划
   - 集成测试方案
   - 测试用例列表
   - 验收测试标准

## 使用示例

**用户**: "我要开发一个天气查询工具，请帮我规划设计"

**AI**: 
```
我将按照 SPEC 范式帮你规划这个项目。首先让我了解一些细节：

1. 这个工具需要支持哪些城市或地区？
2. 需要显示哪些天气信息（温度、湿度、风力等）？
3. 是否需要历史天气查询功能？
4. 你希望使用什么技术栈？

请告诉我你的想法，我会据此生成 spec.md 文件。
```

**用户回答后**:
```
好的，根据你的需求，我生成了 spec.md 文件：

[spec.md 内容]

请阅读 spec.md，如果没有问题，请告诉我"继续生成 requirement.md"
```

## 注意事项
- 每一步都需要等待用户确认后再继续
- 生成的文档应该清晰、具体、可执行
- api.md 中的伪代码应该足够详细，便于后续开发
- test.md 应该覆盖所有关键功能和边界情况

## 输出格式
所有生成的 md 文件应该：
- 使用清晰的标题层级
- 包含必要的代码块和示例
- 使用表格展示结构化数据
- 保持专业且易读的排版
